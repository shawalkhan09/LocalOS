# LocalOS — Project Status

This file is the single source of truth for what has shipped, what's in
review, what's known-broken, and what's next. Update it after every
session or group of chunks — do not let it drift from reality.

## What this is
LocalOS is a config-driven booking/CRM/dashboard platform for local service
businesses. Built as a portfolio piece and a live sales demo for freelance
client outreach. The live demo is "Ironclad Fitness" (a gym), configured
via `clients/gym-demo/config.json`.

**Architecture decision (final, do not revisit):** single-tenant per
deployment, not multi-tenant SaaS. One core engine, config-driven per
business, deployed separately per client with its own database. This was
a deliberate, considered choice — never propose multi-tenancy.

## Stack
- npm-workspaces monorepo: `apps/api` (Express), `apps/web` (Next.js),
  `packages/config-schema` (zod), `packages/db` (Drizzle ORM + Postgres)
- Deployed on Vercel (web) + Render (API, free tier) + Neon (Postgres,
  free tier)
- Auth: opaque session tokens in an httpOnly cookie, bcrypt password
  hashing, two roles only (`owner`, `staff`)
- All date/time logic goes through Luxon and the business's configured
  timezone — never naive `new Date()` arithmetic or the server's own
  timezone. A real cross-timezone bug shipped once already (see Chunk 2)
  because of this.
- No lint script or ESLint config exists anywhere in the repo. Build and
  `tsc --noEmit` (typecheck) are the only automated checks available.

## Working conventions
- Branch naming: `chunk-N-<short-topic>`, created fresh off `main` each
  time, never reused from a prior merged chunk. PR title: "Chunk N: <topic>".
- Commit messages: one-liner, no AI/model attribution.
- Render's API service never auto-deploys despite "Auto-Deploy: On
  Commit" — every deploy requires a manual "Deploy latest commit" click.
  Render only hosts `apps/api`, so a chunk that only touches `apps/web`
  needs no Render step at all.
- Any schema/migration change requires the careful sequence: apply the migration SQL against Neon first (additive only, nullable columns / partial indexes), THEN deploy the API code. Never the other way around. Note: Neon has no `drizzle.__drizzle_migrations` tracking table — earlier migrations were hand-applied as raw SQL, so `drizzle-kit migrate` cannot be run against Neon directly (it would try to replay every migration and fail on tables that already exist). Apply new migration files by hand via `psql`, wrapped in a transaction, rehearsed with `ROLLBACK` before the real `COMMIT`. Plain code-only chunks (no schema change) just need merge + Render manual deploy (only if `apps/api` changed) + Vercel auto-build.

## Chunks shipped
1. **Customer archive/unarchive** (soft delete via `archivedAt` column).
   Available to both owner and staff.
2. **Booking time validation**: rejects past times, enforces business
   hours, advance-booking window, duration match, same-customer double-
   booking, class-weekday validation, duplicate class-seat rejection.
   Shipped with a real cross-server-timezone bug (valid evening bookings
   rejected when server timezone ≠ business timezone), found and fixed
   before merge. Manually re-confirmed live 2026-09-20.
3. **Password management**: self-service `POST /auth/change-password`
   (keeps current session alive, signs out all others) and owner-only
   `POST /users/:id/reset-password` (no current-password proof needed,
   blocks self-targeting, forces full logout of the target account). Web
   UI: `/dashboard/account` page + Team page reset action.
4. **Staff account linking constraint**: a staff member can now be linked
   to at most one login account (DB-level partial unique index on
   `users.staffId`), with a friendly 409 instead of a raw DB error. A
   deploy-breaking bug was fixed during review: the migration SQL was
   correct but `migrations/meta/_journal.json` was never updated, so
   `drizzle-kit migrate` would have silently applied nothing.
5. **Staff schedule view**: logged-in staff members can view their own
   upcoming sessions and classes for the next 14 days on `/dashboard/schedule`.
   API endpoint `GET /staff/me/schedule` returns bookings assigned to the
   staff member's staffId plus class occurrences where the class trainerId
   maps to a trainer with that staffId. Classes *are* included: built from
   config.json class definitions + trainer_profiles DB link, not a separate
   DB table. If account is not linked to a staff member, returns `linked: false`
   with empty items. Navigation: "My schedule" link visible only to staff role.
   A blocking bug was found and fixed during review: `usersRouter.use(requireOwner)`
   and `staffRouter.use(requireOwner)` were unscoped blanket router middleware,
   which in Express applies to every request reaching that router, not just
   routes defined on it — since `usersRouter` was mounted right before
   `staffRouter`, every staff-role request to any `staffRouter` route (including
   the new schedule endpoint) was rejected with 403 before reaching its handler.
   This predated this chunk but was invisible until now because every existing
   staffRouter route was already owner-only. Fixed by replacing both blanket
   `.use(requireOwner)` calls with `requireOwner` as an explicit per-route
   middleware on each of the eight owner-only routes across both files.
   A second bug was found and fixed after initial deploy: the schedule page displayed all times in the viewer's browser timezone instead of the business's configured timezone (e.g. a 6:00 AM class showed as 5:00 PM for a viewer in a different timezone), and grouped items by UTC calendar day instead of the business's calendar day. Fixed in PR #8 by reusing the existing formatTimeInTimezone/formatDateInTimezone helpers in apps/web/src/lib/time.ts (already used correctly elsewhere, e.g. new-booking/page.tsx) instead of raw, timezone-naive Date formatting.
6. **Small UI bug fixes** (PR #10, fix-small-ui-bugs, merged to main at commit 8bad23e): Stale password-mismatch error on /dashboard/account now clears on input change, not just on resubmit. Password validation errors return a clean message instead of a raw Zod JSON blob (password-related throw sites only: POST /auth/change-password, POST /users, POST /users/:id/reset-password). Mobile account menu click-outside-to-close now works. Mobile account menu is now visible at every viewport width (fixed a CSS specificity tie between two .mobileAccountContainer rules with identical specificity, one unconditional display: none and one in @media (max-width: 639px) with display: flex — the later rule was always winning due to source-order specificity tie-breaking; moved the unconditional rule before the media query so the media query override wins at narrow widths).
7. **Chunk 4b: Mobile account menu** (PR #5, merged to main): adds a compact "Account" button in the mobile nav (below 640px) with a toggle menu for "Change password" and "Log out," reusing the existing handler and route unchanged. Web-only, no schema change. Its missing click-outside-to-close and a CSS bug that hid the menu at every viewport width were both fixed later in PR #10 (entry 6).
8. **Class booking default date fix** (PR #15, fix-class-booking-default-date, merged to main): the public class-booking page now defaults to the next date the selected class actually runs, counted from today in the business's timezone and inside the advance-booking window. A day only counts if the class runs on that weekday and, for today, the class start time is still in the future (matching the API's "already started" rule). Picking a date the class does not run, or today after the class has started, shows an inline message and disables Continue; a class with no bookable date in the window shows a friendly message instead of the form. Web-only: added nowTimeInTimezone and getNextClassOccurrenceDate to apps/web/src/lib/time.ts. Verified live on 2026-09-21.
9. **Cancel booking** (PR #16, chunk-6-cancel-bookings, merged to main): owner and staff can cancel a confirmed booking or a booked class seat from the Today dashboard via a two-step Cancel → Confirm cancel/Keep control. New endpoints `POST /bookings/:id/cancel` and `POST /class-bookings/:id/cancel` (atomic conditional update, no `DELETE`, any authenticated role). The Today page gained a date picker (defaults to today, guards against invalid partial input) and a new per-attendee "Class bookings" table (previously only the aggregate "Classes" table existed). Required two migrations so a cancelled row frees up its slot: the staff-overlap GiST exclude constraint and the class-booking uniqueness constraint were both changed to ignore cancelled rows. Applied by hand against Neon after a full local rehearsal and a Neon branch backup (`pre-chunk6-backup`). Verified against a local scratch DB, curl, and the live browser UI before merge. Used afterward, live, to cancel the test/demo data noted below.
10. **Backlog fixes + demo timezone switch to Asia/Karachi** (PR #17, chunk-7-bugfixes-and-timezone, merged to main): three backlog bugs fixed, plus the demo's business timezone changed. (a) `apps/api/src/index.ts`'s `listen()` no longer silently swallows bind failures — a `server.on("error", ...)` handler now logs the failure and exits non-zero instead of a port conflict logging "api listening" (or, before this fix, crashing with an unhandled exception). (b) `localWeekday`/`formatDateInTimezone`/`addDaysToDateString` in `apps/web/src/lib/time.ts` no longer misfire at UTC+12 and later (verified against Pacific/Kiritimati, UTC+14) — they previously anchored on a fixed noon-UTC timestamp, which had already rolled into the next calendar day at those offsets; the API's own `localWeekday` (in `apps/api/src/availability.ts`) was checked and confirmed already correct (Luxon-based), so it needed no change. (c) `assertBookableClassOccurrence` in `apps/api/src/bookingWindow.ts` now checks every schedule slot for the matching weekday instead of only the first, so a class scheduled twice on one weekday can no longer pass the booking page's validation and then fail (409) at confirmation. (d) `clients/gym-demo/config.json`'s `business.timezone` changed from `America/Denver` to `Asia/Karachi` (PKT, UTC+5) — confirmed that `apps/api` loads this file once into memory at process start (not per-request), so a timezone change needs a Render manual redeploy to take effect; `apps/web` never reads the file directly and instead fetches it live via the API's `/catalog` endpoint on each page load, so no Vercel rebuild is required for the change itself to apply (Vercel still auto-builds on push, it's just not what makes the new timezone live). Verified live post-redeploy: displayed "today" date/time matched current Asia/Karachi time, not Denver.
11. **Design system foundation: dark/premium theme + shared components** (PR #18, chunk-8-design-tokens, merged to main): established the visual foundation for a UI overhaul — no page redesigns yet, tokens and components only. Added CSS custom properties in `apps/web/src/app/globals.css` for color (dark palette: `--color-bg: #0B0F1A` through `--color-danger`), an 8px-based spacing scale, a type scale, and radius tokens; legacy token names (`--bg`, `--accent`, etc.) are aliased to the new ones so every existing page picked up the dark theme automatically without per-page migration. Added Plus Jakarta Sans (UI) and JetBrains Mono (dates/times/numeric values) via `next/font/google`. Added four shared components (`Button`, `Card`, `StatusPill`, `Input`) under `apps/web/src/components/`, not yet wired into existing pages. `--color-accent` is computed server-side per client deployment: `apps/web/src/app/layout.tsx` is now an async Server Component that fetches the business config's `primaryColor` and injects both `--color-accent` and a computed `--color-accent-foreground` (picked between white/dark text based on WCAG contrast against the accent, since a single hardcoded foreground can't guarantee 4.5:1 against an arbitrary config-driven brand color) as inline styles on `<html>`, avoiding any client-side flash of a fallback color. A global CSS rule gives unclassed `input`/`textarea`/`select` elements sane dark styling so untouched pages don't look broken against the new background. Verified end-to-end: server-rendered HTML confirmed to carry the real computed accent values (not just the CSS fallback), contrast ratios recomputed and documented in `apps/web/DESIGN.md` (`--color-danger` and `--color-text-muted` were adjusted to clear 4.5:1; the accent-foreground pairing is a documented known limitation for saturated mid-luminance brand colors, which cannot hit 4.5:1 with any single foreground choice).

14. **Chunk 11: services moved out of config.json into the database** (PR #21, chunk-11-services, merged to main): services now live in a real `services` table (id, name, description, durationMinutes, price, category, staffIds — same shape and same move as staff/trainer_profiles in an earlier round), dashboard-editable at `/dashboard/services` (owner-only, same table+form pattern as the Staff page). `bookings.serviceId` also got the same FK upgrade staff went through: it's now a real foreign key against `services.id` instead of plain validated text, since the service catalog is no longer config-driven. Migration `0005_pale_tinkerer.sql` (`CREATE TABLE services` + the FK on `bookings.service_id`) was applied against production Neon in the same staged, careful sequence as PR #16's cancel-booking migration: (1) a Neon branch backup (`pre-chunk11-backup`, off `main`, auto-delete after 7 days) was taken first; (2) `CREATE TABLE services` was applied directly (purely additive); (3) the one-time cutover script `migrate-services-from-config.ts` (mirrors `migrate-staff-from-config.ts` — a frozen snapshot of the 4 services that were in `clients/gym-demo/config.json`, `onConflictDoNothing` for idempotency) ran against production and inserted all 4 rows with their preserved ids, giving existing `bookings.service_id` values (including the demo data's `svc-fitness-assessment`) a matching row; (4) the FK-adding `ALTER TABLE` was rehearsed with `BEGIN`/`ROLLBACK` against the real production `bookings` data first, confirmed clean, then committed for real. Verified live afterward: `GET /catalog` through the deployed app (still running the pre-chunk-11 API code/config at that point) continued to return the same 4 services unaffected, and a direct query joining `bookings` to the new `services` table confirmed existing `svc-fitness-assessment` bookings resolve against the new FK. `config-schema`'s `BaseConfigSchema` no longer requires a `services` key (removed from `base.ts`), `gym.ts`'s `assertUniqueIds` call for services was dropped (the table's primary key enforces that now), and `ClientConfigSchema` (`index.ts`) gained `services` back as a database-backed field, same as `staff`/`trainers` — so `GET /catalog`'s response shape is unchanged and `apps/web` needed no changes to existing pages that already read `config.services`. `clients/gym-demo/config.json` no longer carries a `services` key. New owner-only routes: `POST/PATCH/DELETE /services` (validation in `apps/api/src/validation.ts`: `CreateServiceSchema`/`UpdateServiceSchema`, same `.strict()` + "at least one field" style as staff's). Unlike staff (which deliberately has no DELETE — see its comment in `routes/staff.ts`), services got a real DELETE: the new FK is the actual guarantee, and a service still referenced by a booking is rejected at the database level (23503) and surfaced as a friendly 409 ("This service can't be deleted because it has existing bookings.") by a new named branch in `app.ts`'s error handler, not a raw Postgres error or a silent orphan. `requireOwner` applied as explicit per-route middleware on each of the three new routes, not a blanket `.use(requireOwner)` — chunk 5 already shipped a real bug from that shortcut once (see entry 5), not repeating it. A wider ripple than services itself: since services are no longer part of the parsed `GymConfig`, every place that used to read `clientConfig.services` (`bookingRules.ts`'s `findService`, `routes/availability.ts`, `routes/staff.ts`'s schedule-label lookup, `bookingWindow.ts`'s `assertBookableSessionTime` param type, and the `check.ts` smoke test) was switched to a DB lookup instead — required for the schema change to typecheck at all, not optional cleanup. Verified end-to-end against a local rehearsal database before touching production: created a service through the real API, confirmed it appeared in `GET /catalog`, booked against it, confirmed `svc-fitness-assessment` still resolves (matches `seed-demo-data.ts`'s reference), confirmed update works, confirmed delete is blocked (409) while a booking exists and succeeds (204) once unreferenced. Dashboard page screenshotted (real PNG files, via a locally-installed Playwright driving a real Chromium instance — the in-app browser tool alone can't save screenshots to disk) at 375px and 1280px — the services table uses the same horizontal-scroll fallback as Staff/Team's dense tables at narrow widths, no new clipping bug. **Render still needs a manual "Deploy latest commit" click** (touches `apps/api`) before the live API actually starts reading/writing `services` from the database instead of `config.json` — not done as part of this chunk.

15. **Chunk 13: business hours moved out of config.json into the database** (PR #23, chunk-13-business-hours, merged to main): business hours now live in a real `business_hours` table (`day` as the primary key, `openTime`, `closeTime` — `day` stays `text`, not a pgEnum, same runtime-checked reasoning as `classes.trainerId`), dashboard-editable at `/dashboard/business-hours` (owner-only). Same overall pattern as chunks 11/12 (services, classes), but simpler: business hours is a bounded 7-day settings object with a natural key, not an owner-managed list needing generated ids, and it lives in *base* config (`base.ts`) rather than a gym-specific file, since every vertical needs hours checked, not just the gym one. Migration `0007_cultured_vivisector.sql` (`CREATE TABLE business_hours`) is purely additive, same staged pattern as prior chunks. The one-time cutover script `migrate-business-hours-from-config.ts` (mirrors `migrate-classes-from-config.ts` — a frozen snapshot of the 6 slots that were in `clients/gym-demo/config.json`, `onConflictDoNothing` on `day` for idempotency) has been run and verified locally; it has **not yet been run against production Neon**. `config-schema`'s `BaseConfigSchema` no longer requires a `businessHours` key (removed from `base.ts`), along with the now-dead `assertBusinessHoursValid` helper (deleted entirely rather than left unused); `ClientConfigSchema` (`index.ts`) gained `businessHours` back as a database-backed field, so `GET /catalog`'s response shape is unchanged and `apps/web`'s public landing page needed no changes. `clients/gym-demo/config.json` no longer carries a `businessHours` key. The `closeTime > openTime` check moved out of config-schema's `superRefine` into a new `CreateBusinessHoursSchema` in `apps/api/src/validation.ts` (per-slot `.refine`, plus a separate array-level `.refine` rejecting duplicate days) — same "runtime check, not a config-time one" move `classes.trainerId`'s existence check went through in chunk 12. New owner-only `PATCH /business-hours` (`apps/api/src/routes/businessHours.ts`) is **replace-all**, not add/remove like Services/Classes: it deletes every existing row and inserts the new set inside one DB transaction, so a failed request never leaves the table half-updated; a day omitted from the array is simply not re-inserted, i.e. closed. Both call sites that read business hours (`bookingWindow.ts`'s `assertBookableSessionTime` and `routes/availability.ts`'s check-availability) were switched from `clientConfig.businessHours` to a new shared `getBusinessHours()` DB helper in `bookingRules.ts`, so they don't each write their own near-identical query — this makes `assertBookableSessionTime` **async**, so every caller (`routes/bookings.ts`, `routes/public.ts`, and roughly a dozen call sites in `apps/api/src/check.ts`) now awaits it. New dashboard page `apps/web/src/app/dashboard/business-hours/page.tsx`: one row per weekday in fixed Mon–Sun order, a closed/open toggle per day, open/close time inputs shown only when open, and a single "Save" button that PATCHes the whole week at once — a settings form, not a table with individual add/remove actions. Verified end-to-end against a local Postgres + a running API instance before pushing: the generated migration applies cleanly, the cutover script is idempotent, `PATCH /business-hours` accepts a valid week and correctly rejects `closeTime <= openTime` and duplicate days with 400s and unauthenticated requests with 401, `GET /catalog` reflects saved changes, and the dashboard page (driven through a real browser) loads live data, toggles Sunday open with the expected default times, saves, and shows a success toast — demo data was reverted to its original 6-day set afterward. `packages/config-schema` and `packages/db`'s own `check` scripts both have pre-existing, unrelated failures on `main` (confirmed via `git stash` before this change — they date from services leaving `config.json` in chunk 11) and were left untouched. **Production rollout not yet done**: the staged Neon sequence (branch backup, additive `CREATE TABLE`, cutover script, row-count/spot-check against `config.json`, then drop the `businessHours` key from `config.json` on deploy) and the Render manual deploy are still pending.
